1. Punto de partida y alcance

El grupo ya cuenta con un documento de análisis, una tabla de componentes y código PlantUML para los diagramas de clases y componentes. Esta propuesta los toma como base y propone implementar cinco requisitos seleccionados en el Word y uno adicional de cancelación, junto con las operaciones auxiliares necesarias.

Estado: el backend está implementado y probado (67 pruebas automáticas): los seis requisitos, el inicio de sesión con roles, la administración de cuentas, productos, proveedores, inventario, clientes, ventas con reserva, anulación y despacho. Una aplicación Spring Boot reúne los componentes. Se propone un proyecto Maven con paquetes por área y límites explícitos entre sus interfaces; las carpetas por sí solas no garantizan reutilización. La fachada ofrece acceso organizado y delega operaciones; la API HTTP es el mecanismo de comunicación con los clientes.

Reutilización y fachada

Se diseñan interfaces para que los componentes puedan ser usados por otros consumidores. Ventas y Entregas reutilizan servicios de Bodega; ambos clientes consultan la misma disponibilidad por la API. El componente que actúe como fachada debe existir en el código y delegar: el simple hecho de tener rutas HTTP no demuestra el patrón.

Los componentes de negocio se construirían para esta actividad; no se afirma que provengan de un proyecto anterior. Se diseñan para su reutilización y se usan con reutilización dentro de la solución.

¿Qué habría dentro de un componente?

Por ejemplo, bodega/ agruparía sus modelos de negocio, la interfaz que ofrece a otros componentes, el servicio que aplica sus reglas y la persistencia. Las subdivisiones dominio, aplicacion e infraestructura son una opción para ordenar responsabilidades; no es necesario crear archivos o interfaces vacíos solo para completar carpetas.

bodega/                                  Ejemplo conceptual
├── api/                                 Lo público: IInventario y sus DTO
├── dominio/                             Producto, Existencia, Reserva y sus repositorios (interno)
├── aplicacion/                          Servicios que implementan la interfaz (interno)
└── infraestructura/                     Solo si hay tecnología concreta (interno)

Regla: los demás componentes solo pueden usar el subpaquete api de otro. dominio y aplicacion son internos; una prueba con ArchUnit lo comprobará. Es la convención de Spring Modulith: lo público se separa de lo interno.

Esta organización está inspirada en arquitectura hexagonal: el dominio expresa reglas del negocio; la aplicación coordina operaciones y contratos; la infraestructura conecta con tecnologías concretas. Es un monolito modular propuesto, no una afirmación de hexagonal estricta. Las subdivisiones y clases son ejemplos; se crean solo las necesarias y se ajustan al modelo del grupo.

El registro de usuario coordina Terceros, Recursos Humanos y Seguridad según sus contratos; no duplica personas ni aprueba el aval automáticamente. Flujo de ejemplo: Ventas solicita una reserva a IInventario; la implementación de Bodega comprueba disponibilidad y persiste el cambio. El controller recibe HTTP y la fachada organiza y delega las operaciones para los clientes. No se debe acceder directamente a los detalles internos de otro componente solo por compartir aplicación o base de datos.

Por acordar con el grupo: ubicación de cada interfaz y fachada, dependencias entre componentes, configuración de transacciones y control de concurrencia, nombres de paquetes y diferencias con la propuesta original de módulos Maven. Mantener la coherencia con las clases y relaciones de los diagramas finales.

4. Clases, base de datos e inventario

El diagrama de compañeros guía el modelo: Tercero, Usuario, Empleado, Vendedor, AvalRH, Cliente, Producto, Existencia, Venta, DetalleVenta, Proveedor, Entrega y MovimientoInventario. No es obligatorio implementar cada método del modelo general si no interviene en el alcance.

Adición para reservas: ReservaInventario se asocia a una venta; DetalleReserva identifica cada producto y cantidad. Estados propuestos: ACTIVA, CONSUMIDA y LIBERADA. La cantidad reservada puede obtenerse sumando detalles activos.
Disponible = stock físico − unidades reservadas

Inicial:       físico 10  | reservado 0 | disponible 10
Venta de 6:    físico 10  | reservado 6 | disponible  4
Despacho:      físico  4  | reservado 0 | disponible  4
Cancelación antes del despacho: libera la reserva; el físico no cambia.

Usaremos una base PostgreSQL con un esquema por componente (seguridad, terceros, recursos_humanos, ventas, bodega, proveedores, entregas). Un esquema es una carpeta de tablas dentro de la misma base: cada componente solo toca las suyas y se refiere a las de otro por identificador, sin llaves foráneas entre esquemas. Así se respeta la idea del Word de que cada área tiene sus propios datos, pero una venta puede reservar y guardar en una sola transacción. PostgreSQL se ejecuta con Docker Compose y el backend corre localmente durante el desarrollo. El almacenamiento de PostgreSQL debe configurarse para conservar los datos entre reinicios. Los atributos persistentes se mapean a datos; los métodos representan comportamiento en Java y no se convierten automáticamente en columnas.

Una venta con varios productos se registra con todas sus reservas o no se registra; la cancelación libera todas las reservas activas; el despacho solo se aplica una vez. La comprobación y reserva deben coordinarse para impedir que dos solicitudes reserven las mismas unidades. Estas garantías requieren transacciones, control de concurrencia y pruebas sobre PostgreSQL.

La alerta de bajo stock se propone cuando cantidad disponible < stock mínimo.

Estados y cambios al modelo

  • Venta: PENDIENTE_ENTREGA, DESPACHADA y ANULADA. Registrar y quedar pendiente ocurren en el mismo paso, y el flujo termina al despachar.
  • Entrega: se crea al despachar con estado DESPACHADA. ENTREGADA y FALLIDA quedan como ampliación futura.
  • MovimientoInventario: tipos ENTRADA, SALIDA y AJUSTE; guarda cantidad anterior y nueva, motivo, referencia (por ejemplo VENTA-12) e idUsuario en lugar del nombre.
  • Entrega: receptor guarda el nombre del cliente e idResponsable el usuario que despacha. Se retira confirmar(), que no se implementa.
  • Producto: campo activo. Bodega: hay una sola fila en la tabla y no se mapea como entidad.
  • Usuario: incorpora el atributo rol (RECURSOS_HUMANOS, VENDEDOR, BODEGA o ENTREGAS).
  • Clases nuevas: ReservaInventario y DetalleReserva, con estados ACTIVA, CONSUMIDA y LIBERADA.

5. Inicio de sesión, roles y aval

La autenticación identifica a la persona; los roles determinan sus permisos; el aval expresa la autorización de Recursos Humanos para actuar como vendedor. Se propone Spring Security con sesiones administradas por el servidor, sin OAuth. Cada cliente mantiene su propia sesión; el backend identifica al usuario autenticado y no confía en un identificador enviado por el cliente para suplantar al vendedor.

Rol propuestoPermisos para esta versión
RECURSOS_HUMANOSCrear cuentas de Vendedor, Bodega y Entregas; modificar datos y desactivar cuentas; consultar vendedores y aprobar avales. No crea cuentas de RH, no cambia el rol de una cuenta y no puede desactivar su propia cuenta.
VENDEDORCon aval aprobado: consultar productos, registrar y actualizar clientes y crear ventas. Puede cancelar sus propias ventas pendientes incluso sin aval vigente, siempre que su cuenta esté activa.
BODEGARegistrar y actualizar productos y proveedores, asociarlos; consultar inventario y registrar entradas y ajustes con motivo.
ENTREGASConsultar ventas pendientes y despachar.

Cada cuenta tiene un solo rol de acceso. RH puede asignar VENDEDOR, BODEGA o ENTREGAS; la cuenta inicial de RH se crea para desarrollo. El vendedor sin aval vigente no puede crear ventas, pero sí cancelar sus propias ventas pendientes si su cuenta está activa. Entregas puede despachar ventas aceptadas aunque el vendedor haya perdido el aval. Un rol de negocio de Tercero (cliente, empleado o proveedor) es distinto de un rol de acceso. La cuenta se vincula a un tercero; un cliente no necesita necesariamente una cuenta. Para cambiar el rol de alguien se desactiva su cuenta y se crea otra. RH define la clave inicial; no hay cambio de contraseña en esta versión (RF-25 queda fuera de lo implementado).

Seguridad debe aplicar permisos en el backend y verificar el aval vigente en las operaciones de vendedores que correspondan. Sesión: cookie de sesión del servidor con protección CSRF de Spring (cookie XSRF-TOKEN y encabezado X-XSRF-TOKEN), que Angular maneja de forma nativa; el cliente C++ guarda la cookie y reenvía el token. Expira a los 30 minutos sin actividad. En un despliegue accesible por red se requiere HTTPS; el HTTP local se limita a pruebas.

La desactivación bloquea la cuenta e invalida sus sesiones. Si es un vendedor con ventas pendientes, esas ventas siguen pendientes y Entregas puede despacharlas; nadie las cancela mientras la cuenta esté inactiva. Un ajuste no puede dejar stock físico negativo ni inferior a las unidades reservadas; debe guardar el actor autenticado, fecha, motivo, valor anterior y nuevo. La salida por una venta la solicita Entregas mediante el despacho.

8. Datos y pruebas de demostración

Con el perfil dev se cargan: una cuenta de RH, una de Bodega, una de Entregas, una vendedora con aval aprobado y un vendedor con aval pendiente, el proveedor «Distribuidora Ejemplo», tres productos con existencias (el azúcar queda bajo su mínimo) y dos clientes. RH también podrá crear usuarios desde el escritorio mediante la API. Son datos ficticios para demostrar los flujos.

Cómo se prepararían en cada computador

  1. PostgreSQL en Docker: un docker-compose.yml en la raíz; cada integrante levanta su propia base local con docker compose up -d. Los datos se conservan en un volumen; reiniciar el contenedor no debe borrarlos.
  2. Esquema con Flyway: el proyecto incluirá migraciones SQL versionadas en src/main/resources/db/migration/. La primera migración crea los esquemas por componente. Al iniciar el backend, Flyway aplica las migraciones pendientes y registra cuáles ya se ejecutaron. Crear tablas o relaciones y cargar ejemplos son pasos distintos.
  3. Datos de demostración: un cargador de Spring Boot que solo actúa con el perfil dev. Comprueba si la cuenta inicial ya existe antes de cargar; reiniciar no duplica datos ni borra cambios. Crea las cuentas rh@, bodega@, entregas@, ana@ (vendedora con aval aprobado) y luis@ (aval pendiente), todas @polimarket.test y con la clave ficticia de application-dev.yml. Para las contraseñas de cuentas ficticias se usará el codificador de contraseñas de Spring Security; nunca se guardarán credenciales reales en el repositorio.
  4. Pruebas repetibles: las pruebas automatizadas usan una base PostgreSQL aislada y desechable (Testcontainers) y crean sus propios datos controlados; no deben borrar ni alterar la base de demostración. Si se necesita reiniciar una demostración, el procedimiento será explícito y documentado.
Varios computadores: el repositorio contiene migraciones, cargador e instrucciones, no la base con sus datos cambiantes. Cada integrante obtiene la misma estructura y datos iniciales en su base local, pero las ventas nuevas de uno no aparecen en la base de otro. Para una demostración conjunta en tiempo real, ambos clientes deben conectarse al mismo backend y a su misma base, con acceso configurado de forma segura.

Flyway (migraciones V1 a V9) y el cargador están implementados. Una migración versionada no se repite en cada arranque: si cambiamos una tabla después, agregamos otra migración.

Recorrido de pruebas

  1. En el escritorio, iniciar sesión con la cuenta inicial de RH, registrar una persona o seleccionar un tercero existente, crear su cuenta y comprobar que su aval sigue pendiente; luego aprobarlo.
  2. Iniciar sesión como vendedora; comprobar que un vendedor sin aval no puede vender.
  3. Consultar disponibilidad desde ambos clientes.
  4. Registrar una venta de 6 unidades cuando hay 10: quedan 10 físicas, 6 reservadas y 4 disponibles.
  5. Intentar reservar una cantidad superior a la disponible; verificar que se rechace sin cambios parciales.
  6. Cancelar una venta propia pendiente y verificar que su reserva se libera; impedir cancelar la venta de otra persona.
  7. Registrar otra venta, despacharla y verificar la salida; rechazar un despacho duplicado.
  8. Consultar productos bajo stock y sus proveedores.
  9. Comprobar que cada cliente consume al menos dos funcionalidades y que los permisos se aplican en el backend.

Cómo se prueba hoy

  • ./mvnw test en backend/: 67 pruebas en unos 35 segundos (unitarias, de API y de concurrencia), cada una sobre PostgreSQL en un contenedor desechable.
  • bash docs/probar-api.sh: recorrido manual de RSI-1 con curl.
  • bash docs/probar-flujo-venta.sh: recorrido de RSI-2 a RSI-6 con los datos de demostración.

Concurrencia comprobada con hilos reales: 20 ventas simultáneas de una unidad sobre 10 en bodega dejan exactamente 10 reservas; 5 despachos simultáneos de la misma venta dejan una sola entrega y el stock descontado una vez; 5 aprobaciones simultáneas del mismo aval dejan un solo registro. Una venta con varios productos donde uno falla no deja ni la venta ni reservas parciales.

Cómo se ve una fachada y un servicio

// fachada/: no tiene reglas, solo organiza y delega
@Service
public class FachadaPoliMarket {
    private final IVentas ventas;
    private final IInventario inventario;
    private final IAutorizacion autorizacion;

    public VentaCreada registrarVenta(long vendedorId, SolicitudVenta s) {
        return ventas.registrar(vendedorId, s);
    }
    public List<ProductoDisponible> listarProductos() { return inventario.listarDisponibles(); }
    public EstadoAval consultarAval(long vendedorId)  { return autorizacion.consultar(vendedorId); }
}

// ventas/aplicacion: las reglas de Ventas, usando solo interfaces de otros componentes
@Service
class VentasService implements IVentas {
    @Transactional
    public VentaCreada registrar(long vendedorId, SolicitudVenta s) {
        if (!autorizacion.estaAutorizado(vendedorId)) throw new VendedorSinAvalException();
        Venta venta = Venta.crear(vendedorId, s);          // calcula precios y total
        ventasRepo.guardar(venta);
        inventario.reservar(venta.getId(), s.productos());  // todo o nada
        return VentaCreada.de(venta);
    }
}

Cómo se evita vender dos veces las mismas unidades

@Transactional
reservar(ventaId, items):
  ordenar items por productoId                 // mismo orden siempre: evita bloqueos cruzados
  por cada item: SELECT … FROM bodega.existencia WHERE producto_id = ? FOR UPDATE
  disponible = cantidad_fisica − suma(detalle_reserva ACTIVA del producto)
  si disponible < cantidad → lanzar STOCK_INSUFICIENTE   // la transacción se revierte completa
  insertar reserva ACTIVA y sus detalles

El bloqueo de fila hace que dos ventas del mismo producto se atiendan una tras otra, no a la vez.

Cómo se hace una funcionalidad nueva

  1. Si necesita tablas: nueva migración Flyway (V2__…sql).
  2. Regla de negocio en el dominio o el servicio del componente.
  3. Método en la interfaz del componente (IInventario, IVentas…).
  4. Método en la fachada y endpoint en el controller.
  5. Prueba que lo ejercite.
